# 管理器异常恢复

采集及其子进程仍绑定管理器的 Windows Job：管理器结束时一起结束，NapCat 保留独立运行能力。

已修正启动确认的时序问题。主界面繁忙跨过启动期限时，先收取启动进程已经完成的结果，再检查后端是否属于当前管理会话。真实超时仍停止整个会话；待执行的下一次重启不会被旧期限误杀。

## 自动恢复

通过 `scripts/windows/configure-manager-recovery.ps1` 安装当前用户的交互式 Windows 计划任务。默认未安装时不开启。任务每分钟运行一次短检查，没有新增常驻守护进程，也不加载聊天数据或 AI 配置。

- 管理器的 PID 和原生创建时间都匹配且存活：不操作。
- 用户点击停止或退出、或调用停止入口：写入持久停止标记，之后不自动启动。
- 管理器消失，当前登录会话仍已授权恢复：启动管理器，连同其采集服务恢复。
- 十分钟内最多恢复三次，防止持续故障造成快速重启循环。启动失败也消耗一次尝试。
- 无法确认进程身份、登录会话或重试状态时不贸然启动。
- 重启电脑、注销后重新登录，不会由恢复任务额外打开管理器。原有开机自启动入口仍决定是否开启；正常开启管理器并启动采集后才会重新授权本次登录会话的恢复。系统时钟大幅调整导致身份核验失败时，也需要手动启动一次重新授权。

用户手动启动或重启入口会清除停止标记及本轮重试限制。直接运行管理器主程序也可重新启动。请用托盘或管理器内的“停止”“退出”表达主动停止；任务管理器强制结束会被视为异常消失。

不使用 Task Scheduler 的 `RestartOnFailure` 作为恢复依据。本机隔离实测中，该属性没有对退出码 7 触发重试；已改为明确的周期检查，并验证周期触发和短任务退出后子进程存活。

卸载：先正常停止管理器，再执行 `scripts/windows/configure-manager-recovery.ps1 -Uninstall`。

## 排查记录

- `logs/manager-lifecycle.jsonl`：管理会话、启动命令进程、完成状态和耗时、后端接纳及原生退出码、主动停止与正常清理。
- `logs/manager-recovery.jsonl`：恢复尝试、重试限制、身份无法确认等状态变化。
- `logs/manager-runtime.log`：保留原有人类可读的故障原因。

以上记录不包含配置密钥、QQ 身份和聊天内容。被操作系统强制终止时，应用本身可能来不及写最后一条记录；周期检查用于恢复这种停止，不代表已经证明此前退出的具体原因。该机制处理进程消失，不强行结束仍存活但暂时繁忙的界面。
