# 图片库、聊天记录收藏与保活防循环设计

## 背景

图片分类视图会把竖图以 `object-fit: cover` 的固定高度缩略图展示，导致主体被裁切。数据库中仍保存图片原始下载地址，但当前图片入库只读取元数据而不验证完整可解码性；例如图片 #53619（2026-09-04）是 PNG，尾部 IDAT 块被截断且没有 IEND。

资源页面以整条消息的关键词给每一个链接分类，导致含“模型/工作流”的长消息把 GitHub、短链、图片床等一起误分。短链也没有以落地地址展示和分类。

原收藏功能会自动保存私聊合并转发的文本。用户需要的是显式地引用某条合并聊天记录，以指令保存其中所有图片，并单独浏览这些图片。群保活和复读还必须忽略机器人自己的回声事件。

## 已批准的交互

### 聊天记录图片保存

仅在私聊中，用户回复一条合并转发消息并输入：

- `/保存图片`：分类为 `未分类`
- `/保存图片 分类名`：分类为指定的安全文件夹名

程序通过 `get_forward_msg` 拉取合并消息，提取全部普通图片，下载、完整性校验并入库。每张图以 `chat_record_saved` 原因记录，`raw_json` 中保存分类、合并消息 ID 和源节点信息。分类视图展示为 `06_聊天记录收藏/<分类名>`。保存结果回复发现数、新保存数、重复数和失败数。

不再自动保存私聊转发；旧 `favorites` 数据不删除。`收藏夹` 命令只提示新的显式保存方式。

### 损坏图重下

所有新下载和修复下载必须经 Pillow 完整载入验证。修复逻辑读取既有 `images` 行的 URL 与保留路径，下载到临时文件，验证通过后用原子替换更新归档文件和对应数据库行；验证失败绝不覆盖旧文件。

提供私聊回复指令：

- `/修复图片 53619`：修复单张图片
- `/修复图片`：扫描所有已归档但无法完整解码的图片

第一版用数据库中已保存的原始 URL 重新下载。若 QQ URL 已失效，结果会明确报告需要重新转发原记录；不猜测不存在的 OneBot 历史取图接口。

### 链接页

链接页对已知短链（例如 `b23.tv`、`xhslink.cn`）尝试解析最终 URL，并将最终 URL 缓存到 `link_metadata.resolved_url`。分类根据最终 URL、路径、页面标题/描述和紧邻的链接上下文进行；单一长消息的泛关键词不再把所有链接都归为模型。

图片床/外链图片、推广跳转和无法确认用途的短链从“高价值资源”筛掉；网盘被标为 `网盘资源`，不默认叫“AI模型”。页面展示为标题、域名、描述、打开和复制链接，而不是将完整长 URL 作为主要视觉内容。

### 自复读与保活

事件入口在任何业务逻辑前排除 `user_id == self_id` 的消息。复读还会要求达到阈值的不同外部发言人；同一人连续发送不触发。清理群成员公告触发的即时保活只接受外部管理员/群主，且按群设置短暂冷却。

## 非目标

- 不建立新的网页后台或收藏管理 UI。
- 不删除旧收藏数据。
- 不在无需用户明确授权的情况下批量重下所有图片；修复操作由私聊命令或本次指定的 #53619 触发。
- 不为短链解析引入新第三方依赖。
